### Что нашлось даже без зоны

**Bright Data сообщает свои ошибки через HTTP 200.** Запрос с несуществующей
зоной приходит как `200`, пустое тело, и заголовок:

```
x-brd-err-code: client_10002
x-brd-err-msg: Authentication failed: zone not found...
```

Адаптер смотрел только на статус — он принял бы это за **успешную выборку
пустой страницы**, триаж вынес бы `THIN_CONTENT`, и факт о **нашей
конфигурации** был бы записан как факт о **сайте**. Это ровно та подмена,
которую контракт провайдеров и существует, чтобы предотвращать.

Исправлено: заголовки `x-brd-err-*` проверяются **до** статуса, и ошибка
зоны даёт `AUTH` — предохранитель провайдера открывается и ждёт человека.

## Роль

Резерв высокой надёжности, **не провайдер по умолчанию**. Это самая дорогая
дверь, и роутер должен доходить до неё только когда более дешёвые совместимые
стратегии не проходят порог уверенности или перестали работать по истории.

Плановые веса (20 / 40) заданы **выше любой стратегии любого более дешёвого
провайдера**. Это не заявление о тарифе вендора: Bright Data считает CPM, и
цена одного вызова не выражается в кредитах Scrape.do. В первой версии я поставил
unlocker в 12 — ниже, чем `super_render` Scrape.do (15), — и «резервный»
провайдер стал бы первым выбором. Тест
`test_it_is_priced_above_the_cheaper_providers` держит этот инвариант.

## Контракт запроса

```
POST https://api.brightdata.com/request
Authorization: Bearer $BRIGHTDATA_API_KEY
{"zone": "...", "url": "...", "format": "raw"}
```

## Стратегии

| ID | Продукт | Рендерит JS | Резерв |
|---|---|---|---:|
| `brightdata:unlocker` | Web Unlocker | нет | 40 |
| `brightdata:unlocker_render` | Web Unlocker + `render=true` | да | 45 |
| `brightdata:browser` | Browser API | да | 80 |

Browser API — отдельный продукт и **отдельная зона**. Без
`BRIGHTDATA_BROWSER_ZONE` адаптер его не рекламирует: иначе роутер выбирал бы
стратегию, каждый вызов которой падает на конфигурации.

## Модель стоимости — и решающая деталь

Биллинг: **CPM, то есть за 1000 успешных запросов**. Считаются только успешные.

**Но:** документация прямо говорит, что при использовании собственных
заголовков, куки или expect-элементов оплата переходит на **все запросы,
включая неуспешные**, потому что вендор больше не контролирует исход.

Поэтому адаптер **не форвардит заголовки вызывающего**. Это не упущение: форвардинг
молча превратил бы каждую неудачную попытку в платную.

Премиум-домены тарифицируются выше без опубликованного множителя — отсюда
намеренно щедрые резервы.

Ответ на один запрос не несёт цифры стоимости, поэтому стоимость помечается
`unattributed`, а не нулём.

## Безопасность

- Ключ и зоны только из окружения: `BRIGHTDATA_API_KEY`, `BRIGHTDATA_ZONE`,
  `BRIGHTDATA_BROWSER_ZONE`.
- Куки и авторизационные заголовки не передаются — и по биллингу, и по безопасности.

## Ограничения

- Нет ключа → разбор реального ответа не проверен вживую.
- Async-режим (`/unblocker/req` + `/unblocker/get_result`) документирован, но его
  ценообразование — нет; не реализован.
- Плановые веса — наша шкала, а не тариф вендора.
