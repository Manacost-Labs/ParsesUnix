# Сложные сайты

«Сложный» здесь означает: данные не лежат в первом же HTML-ответе. Обычно это
одна из трёх ситуаций — страница рендерится в браузере, перед контентом стоит
защита от ботов, или данные приходят отдельным XHR-запросом.

ParsesUnix не пытается «пробивать» такие сайты. Он ищет **наиболее устойчивый
разрешённый способ** получить публичные данные и дальше пользуется им.

## Что запрещено

Обход аутентификации, платного доступа и любого контроля доступа. Решение
CAPTCHA. Переиспользование чужих cookies и сессий. Если сайт явно запрещает
нужный сценарий автоматического доступа, это фиксируется в профиле и отчёте
приёмки — и механика обхода не строится (см. [acceptance](../acceptance/hard-sites/README.md),
где по этой причине исключён один из предложенных доменов).

## CSR: разметка пришла, данных нет

Классическая ловушка — HTTP 200 с пустой оболочкой:

```html
<div id="root"></div>
<script src="/static/main.js"></script>
```

Это **не успех**. Вердикт — `CSR_REQUIRED`, и он разблокирует браузер (L2), но
никогда не разрешает платного провайдера: рендеринг — наша работа, покупать его
не за что.

Определение — по совокупности сигналов, а не по одному маркеру:

- пустой mount-элемент (`#root`, `#app`, `#__next`, …);
- два и более внешних скрипта плюс hydration-маркеры;
- байты скриптов существенно превосходят читаемый текст.

Порог видимого текста — 400 символов: ниже него страница не несёт ни статьи, ни
листинга, ни карточки товара.

### Канарейка не проверяется внутри `<script>`

Отдельная тонкость, стоившая ложных успехов: если канарейка находится только
внутри JS-массива, страница **не отрендерилась**. Поэтому канарейка
сопоставляется с документом без содержимого `<script>`/`<style>`. Теги
сохраняются, поэтому разметочные канарейки (`<article`) продолжают работать.

## Браузер — разведчик, а не транспорт

Chromium дорог. Использовать его на каждый URL, когда он один раз может найти
JSON-эндпоинт, — самая дорогая ошибка на L2.

```text
L2 браузер
  ↓ перехват сети
XHR / fetch / GraphQL с целевыми полями
  ↓ проверка
кандидат маршрута L0
  ↓ решение оператора
дальнейшие запросы идут по L0
```

`ws-probe --browser` выполняет разведку и возвращает кандидатов. Кандидат **не
становится production-маршрутом автоматически** — профиль правит человек.

Разведка честно отличает «API не найден» от «нас заблокировали»: отчёт несёт
`navigation_verdict` и `conclusive`.

## Пул браузеров

Один Chromium на прогон, один контекст на домен. Границы обязательны: лимит
контекстов с вытеснением по давности, лимит страниц на контекст, TTL, и падение
уносит свой контекст, а не оставляет отравленный.

Изоляция доменов — не оптимизация: cookies одного сайта не должны попадать на
другой, поэтому у каждого домена свой контекст.

Измерено на 8 рендерах: 276 мс/страница при запуске браузера на каждую против
56 мс/страница на общем контексте — **4.9×**.

## Защиты и отпечатки отказов

Знакомая защита узнаётся по нормализованной форме отказа (вердикт, код, размер,
маркеры челленджа, заголовки), причём дайджест **не включает домен** — поэтому
знание переносится на новый сайт. Отпечаток может только **переставить**
маршруты; вердикт остаётся за triage, и подсказка не открывает уровень, который
закрыт политикой.

## Важное наблюдение: L2 не «сильнее» L1

Headless-браузер легче фингерпринтится. На `hsreplay.net/decks/` обычный HTTP
отдаёт страницу, а браузер получает `403` и Cloudflare Turnstile. Поэтому
лестница начинается снизу, а альтернативные маршруты на том же уровне важнее
подъёма.
