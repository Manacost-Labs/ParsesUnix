# Безотказное получение страницы: три слоя надёжности

Дополняет `production-scraping-system.md` и `killer-feature-adaptive-cost-router.md`.
Там речь о стоимости и полноте прогона; здесь — о надёжности **одной
страницы**: как сделать так, чтобы отказ на любом из трёх этапов не
превращался ни в потерю данных, ни в эскалацию на платный канал.

## Определение безотказности

> Страница считается полученной, когда её данные записаны в чистую таблицу
> и прошли валидацию. Любой промежуточный успех (200 OK, скачанный HTML,
> распарсенный объект) успехом **не** считается.

Отсюда три слоя, на каждом из которых возможен свой отказ:

| Слой | Отказ | Как выглядит в наивной системе |
|---|---|---|
| 1. Доступ | не отдали контент | 403/503 → эскалация на деньги |
| 2. Извлечение | контент есть, полей нет | «успех» с null'ами |
| 3. Запись | данные есть, БД в непонятном состоянии | полупрогон, дубли |

## Базовый принцип

**У страницы почти всегда больше одной двери.** Вся предыдущая архитектура
неявно предполагала один маршрут (URL → уровень лестницы) и решала отказ
подъёмом по уровням, то есть деньгами. Диверсификация маршрутов даёт
второе измерение, которое почти всегда бесплатно, и его нужно исчерпать
**до** подъёма по стоимости.

```
Наивно:   URL → L1 → блок → L3 (платно)
Правильно: URL → L1 → блок → alt_routes (бесплатно) → L2 → блок → L3
```

# Слой 1. Доступ

## 1.1 Альтернативные маршруты (`alt_routes`)

Один и тот же контент часто доступен по нескольким адресам, и защита на них
разная. Причина системная: WAF настраивают на основной домен, а про
мобильную и AMP-версии забывают — они обслуживают поисковых ботов, и
жёсткая фильтрация там ломала бы SEO.

Порядок перебора (от дешёвого и стабильного к сложному):

| Маршрут | Как строится | Отдаёт |
|---|---|---|
| RSS / Atom | `/feed`, `/rss`, `<link rel=alternate>` | полный текст на многих CMS |
| sitemap.xml | из robots.txt | список URL + `lastmod` |
| JSON-LD в HTML | внутри основной страницы | структурированные данные |
| AMP | `<link rel=amphtml>` | облегчённый HTML, слабая защита |
| Мобильный поддомен | `m.` / `mobile.` | часто без CF-челленджа |
| Print-версия | `?print=1`, `/print/` | чистый текст без скриптов |
| Внутренний API | найден через XHR (см. 1.2) | JSON, самый дешёвый вариант |
| oEmbed | `/oembed?url=` | метаданные, заголовок, автор |
| Кэш поисковика | доступно не всегда | последнее средство, данные могут быть протухшими |

Правила:

- Маршруты пробуются **на текущем уровне лестницы**, до эскалации.
- Каждый маршрут имеет свою схему извлечения в Site Profile (RSS и HTML
  парсятся по-разному, но дают одни поля).
- Статистика успеха ведётся по `(domain, route)` так же, как по уровням —
  ACR учится не только «какой уровень», но и «какая дверь» работает.
- Маршрут, давший данные хуже основного (усечённый текст, нет части
  полей), помечается `degraded`: годится для подтверждения свежести, но
  не для полной записи. Это отдельное состояние, не «успех».

## 1.2 Перехват XHR вместо парсинга DOM

Когда всё-таки запускается браузер (L2) — **снимать сетевые ответы, а не
скоблить HTML**:

```
page.on('response') → фильтр по content-type: application/json
                    → отбор ответов, содержащих целевые поля
                    → сохранение шаблона URL и заголовков в Site Profile
```

Найденный эндпоинт переводит домен на L0 (прямой HTTP к API) **навсегда**:
дальше ни браузера, ни рендера, ни платного уровня. Один браузерный прогон
окупает себя сотнями бесплатных.

Это самый выгодный обмен в системе: разведка браузером (CPU) →
эксплуатация по HTTP (почти ноль). Запускается автоматически при первом
подключении домена и повторно при срабатывании детектора смены защиты.

Проверять у найденного API: пагинацию (лимит, курсор), требуется ли
токен и как он получается, есть ли поля, которых нет в HTML (часто есть).

## 1.3 Прогрев сессии

Холодный запрос на целевой URL выглядит подозрительно: нет реферера, нет
кук, нет истории. Прогрев:

1. Заход на главную или раздел-родитель.
2. Сбор кук (`cf_clearance`, сессионные, sticky-session провайдера).
3. Пауза с джиттером.
4. Целевые URL в рамках той же сессии с корректным `Referer`.

Одна сессия обслуживает пачку URL одного домена — это и надёжнее, и
быстрее, чем холодный старт на каждый URL. Сессия имеет TTL и счётчик
запросов; при первом BLOCKED — пересоздаётся, а не переиспользуется
(«отравленная» сессия тянет за собой серию отказов).

Для scrape.do есть параметр sticky-сессий, для Scrapling —
`FetcherSession` / `StealthySession` с сохранением состояния.

## 1.4 Хеджирование по латентности

Длинный хвост латентности — отдельная причина недобора в окне прогона: не
блок, а «висит». Правило: если запрос превысил `p95` домена, стартует дубль
по следующему бесплатному маршруту, берётся первый успешный ответ, второй
отменяется.

Применяется **только между бесплатными уровнями и маршрутами**. Хеджировать
платный запрос запрещено — это удвоение стоимости ради латентности.

## 1.5 Порядок слоя 1 целиком

```
1. Freshness Scheduler: нужен ли запрос вообще? (304/хэш)
2. Известный API (L0) — если найден
3. Основной URL на политике ACR + прогретая сессия
4. alt_routes на том же уровне
5. Хеджирование при превышении p95
6. Только теперь — эскалация уровня (по вердикту BLOCKED/SOFT_BLOCK)
```

# Слой 2. Извлечение

Здесь живёт самый частый тихий отказ: страница получена, HTML валиден,
данных нет.

## 2.1 Цепочка экстракторов

Порядок по убыванию устойчивости к редизайну:

| # | Источник | Почему устойчив |
|---|---|---|
| 1 | JSON-LD (schema.org) | от него зависит SEO сайта, ломать себе дороже |
| 2 | `__NEXT_DATA__`, `window.__INITIAL_STATE__` | сериализованное состояние приложения |
| 3 | Микроразметка, OpenGraph, `<meta>` | тоже SEO-критично |
| 4 | CSS/XPath-селекторы | ломается при каждом редизайне |
| 5 | Эвристики (readability, плотность текста) | грубо, но не ноль |
| 6 | LLM по снапшоту из R2 | дорого, только для восстановления |

Ключевая мысль: **начинать с 1, а не с 4.** Типовой парсер сразу пишет
CSS-селекторы и ломается при каждом обновлении вёрстки, хотя рядом лежит
JSON-LD, не менявшийся три года.

Экстрактор возвращает не только значения, но и `source` — каким способом
получено каждое поле. Это идёт в провенанс и позволяет видеть в метриках,
что домен «сполз» с JSON-LD на селекторы (сигнал будущей поломки).

## 2.2 Кворум на критичных полях

Для 3–5 ключевых полей (то, без чего запись бессмысленна) — два
независимых экстрактора:

- Совпали → запись, уверенность `high`.
- Один пуст → запись со значением второго, уверенность `medium`, метка.
- Разошлись → **не выбирать молча**: запись в staging с флагом
  `conflict`, алерт. Расхождение обычно означает, что один экстрактор
  зацепил не тот элемент — это ловится только сравнением.

Не применять ко всем полям: удваивает работу без пользы.

## 2.3 Пагинация и полнота обхода

Самая коварная дыра: обход оборвался, парсер отчитался успехом.

Защиты:

- **Сверка с заявленным счётчиком.** Почти каждый листинг пишет «найдено
  1247». Собрали 300 → инцидент, не успех.
- **Дедуп по натуральному ключу.** Повтор id между страницами = пагинация
  зациклилась (частый баг при курсорной навигации).
- **Sitemap вместо листания**, где возможно: сайт сам перечисляет, что у
  него есть.
- **Детект «пустого хвоста»**: последние N страниц подряд без новых id →
  либо конец, либо обрыв; различается сверкой со счётчиком.
- **Лимит глубины** с алертом при достижении — чтобы не молчать при
  бесконечном скролле.

## 2.4 Нормализация до валидации

Перед проверкой схемы: приведение типов, дат к ISO с таймзоной, чисел с
разделителями и валютой, удаление невидимых символов и `&nbsp;`,
нормализация пробелов, декодирование сущностей, приведение относительных
URL к абсолютным. Иначе валидатор бракует корректные данные, а расхождения
экстракторов возникают на пустом месте («1 234,50 ₽» против «1234.5»).

# Слой 3. Запись

## 3.1 Staging → validate → promote

Распарсенное **никогда** не пишется в чистую таблицу напрямую:

```
1. STAGING     все записи прогона в буферную таблицу
2. VALIDATE    схема, диапазоны, обязательность, дрейф null-rate,
               сверка объёма с ожиданием (sitemap/счётчик)
3. PROMOTE     атомарный перенос в чистую таблицу (одной транзакцией
               или через partition swap / ReplacingMergeTree)
4. ROLLBACK    при провале валидации — чистая таблица не меняется,
               staging сохраняется для разбора, алерт
```

Свойство, ради которого это делается: **полупрогона не существует**. Либо
данные годны целиком, либо потребитель видит прежнюю согласованную версию
и знает из алерта, что обновления не было. Наполовину обновлённая таблица
— худший из исходов, потому что о нём никто не узнаёт.

Порог промоушена задаётся на сайт: например, промоутить только если
получено ≥ 95% ожидаемого объёма и null-rate ключевых полей не вырос
более чем в 2 раза к базовой линии.

## 3.2 Идемпотентность

Ключ записи = натуральный id (или нормализованный URL) + версия контента
(хэш). Повторный прогон того же окна не создаёт дублей и не переписывает
неизменившееся. Это то, что позволяет спокойно перезапускать упавший
прогон — без него любой ретрай прогона риск.

## 3.3 Реестр мёртвых зон

URL, не полученные **ни одним маршрутом и ни на одном уровне** за N
прогонов, — в отдельный список `dead_zones` на ручной разбор, с приложенным
снапшотом последнего ответа и историей вердиктов.

Смысл: карантин 404 — это «страница мертва, всё в порядке». Мёртвая зона —
«мы не умеем это брать», и это дефект системы, который должен быть виден
человеку, а не растворяться в статистике.

# Расширение Site Profile

Всё вышеперечисленное — декларативно, код парсеров не меняется:

```yaml
site: example.com
url_classes:
  article:
    alt_routes:
      - {type: json_api, url: "https://example.com/api/v2/posts/{id}", priority: 1}
      - {type: amp,      url: "{url}/amp",                              priority: 2}
      - {type: mobile,   url: "https://m.example.com{path}",            priority: 3}
      - {type: rss,      url: "https://example.com/feed", mode: bulk,   priority: 4}
    extractors:
      - {kind: json_ld,   type: Article}
      - {kind: next_data, path: "props.pageProps.post"}
      - {kind: css,       map: {title: "h1.post-title", date: "time::attr(datetime)"}}
    quorum_fields: [title, published_at]
    canary_selector: "h1.post-title"
    session_warmup: {enabled: true, entry: "https://example.com/", ttl_min: 30}
    pagination:
      expected_count_selector: ".results-total"
      max_depth: 200
    promote_thresholds:
      min_completeness: 0.95
      max_null_rate_growth: 2.0
```

# Интеграция в Fetch Gateway

Расширенный конвейер (изменения помечены `←`):

```
1.  Дедуп / идемпотентность
1b. Freshness Scheduler: нужен ли запрос
2.  Бюджет-гейт
3.  ACR: выбор уровня
3b. ← Прогрев сессии (если требуется профилем)
4.  Исполнение основного маршрута
4b. ← alt_routes при неуспехе, на том же уровне
4c. ← Хеджирование при превышении p95
5.  Triage → вердикт
6.  Валидация контента (канарейка, стоп-сигнатуры)
6b. ← Цепочка экстракторов + кворум
7.  Учёт стоимости и метрик (+ статистика по маршрутам и экстракторам)
8.  Каскад по уровням — только если 4b исчерпан
9.  Снапшот в R2
10. ← Staging → validate → promote
```

# Матрица отказов

| Отказ | Первый рубеж | Второй | Третий |
|---|---|---|---|
| 403/503 антибот | alt_routes | прогрев сессии | эскалация уровня |
| CSR, пустой HTML | найденный XHR-API | JSON-LD в HTML | рендер L2 |
| Смена вёрстки | JSON-LD / next_data | эвристики | LLM по снапшоту + правка профиля |
| Поле пропало | кворум ловит расхождение | дрейф null-rate | staging не промоутится |
| Пагинация оборвалась | сверка со счётчиком | дедуп по id | sitemap как источник |
| Origin лежит | ретрай через 30м/2ч | alt_route (иной хост) | перенос в sweep след. прогона |
| Медленный ответ | хеджирование | таймаут → ретрай | — |
| Кривые данные | нормализация | схема | rollback промоушена |
| Прогон упал посередине | идемпотентность | staging не промоутится | продолжение с очереди |
| Не берётся ничем | dead_zones + алерт | ручной разбор | — |

---

# Метрики надёжности

- `route_success_rate` по `(domain, route)` — какая дверь работает
- доля страниц, взятых **не** основным маршрутом (рост = основной деградирует)
- распределение `extractor_source` по полям (сползание с JSON-LD на CSS)
- `quorum_conflict_rate` — расхождения экстракторов
- `promote_rejection_rate` — как часто прогон бракуется целиком
- размер `dead_zones` и его тренд
- доля доменов с найденным API (цель — расти)

# Definition of Done

1. Для эталонного домена найден и используется внутренний API; браузер не
   запускается ни разу после разведки.
2. Отключение основного маршрута (эмуляция 403) не приводит к платному
   запросу: данные берутся через `alt_route`.
3. Подмена CSS-классов в снапшоте не ломает извлечение — JSON-LD
   отрабатывает, `extractor_source` меняется, алерт о сползании приходит.
4. Оборванная пагинация детектируется сверкой со счётчиком, прогон
   помечается инцидентом, а не успехом.
5. Провал валидации на промоушене оставляет чистую таблицу нетронутой;
   потребитель видит прежнюю согласованную версию.
6. Убийство процесса в середине не создаёт дублей при перезапуске.
7. URL, не берущийся ничем, попадает в `dead_zones` со снапшотом.

# Порядок внедрения (по отдаче на единицу труда)

```
1. Цепочка экстракторов (JSON-LD первым)   — убирает целый класс отказов, день работы
2. alt_routes                              — второе измерение вместо денег
3. Staging → promote                       — гарантия согласованности БД
4. Прогрев сессий                          — дешёвый рост success rate
5. Перехват XHR                            — переводит домены на L0 навсегда
6. Сверка пагинации                        — закрывает тихий недобор
7. Кворум и хеджирование                   — точечно, на критичных полях
```
