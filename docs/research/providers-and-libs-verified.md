## ⚠️ ГЛАВНАЯ ПОПРАВКА К ПРЕДЫДУЩИМ ДОКУМЕНТАМ

В `web-scraper-architecture.md` и `production-scraping-system.md` было
предположение: «провайдеры не тарифицируют 404, значит ретраи мёртвых URL
бесплатны у провайдера». **Это неверно для scrape.do.**

scrape.do тарифицирует как успешные: `2xx`, `400` (от целевого сайта),
`404`, `410`.

Следствие для конкретной проблемы «вечно 404, повторяю запрос, большие
затраты»: каждый повтор мёртвого URL через scrape.do **списывает кредиты**.
Если URL на домене с per-domain профилем (например, автоматический
`super=true`), один такой повтор стоит не 1 кредит, а 10–200.

Правило скилла усиливается: 404 у scrape.do — это **самая дорогая ошибка
из возможных**, потому что она выглядит как отказ, но тарифицируется как
успех. Отсев мёртвых URL до платного канала (фаза A, HEAD-sweep) — не
оптимизация, а обязательный этап.

## scrape.do

```
last_verified: 2026-08-18
docs: https://scrape.do/documentation/
```

### Тарификация по статус-кодам (авторитетно)

| Код | Значение | Списывает кредит |
|---|---|---|
| 2xx | успешный вызов | **ДА** |
| 404 | цель не найдена | **ДА** |
| 410 | цель удалена | **ДА** (по таблице Request Costs) |
| 400 | плохой запрос **к целевому сайту** | **ДА** |
| 400 | плохой запрос **к scrape.do** | нет |
| 429 | превышен лимит конкурентности | нет |
| 401 | нет кредитов / подписка приостановлена | нет |
| 502 | запрос не удался, повторите | нет |
| 510 | запрос отменён HTTP-клиентом | нет |

Если сайт отдаёт 404/400, но для твоей задачи ответ невалиден, scrape.do
предлагает написать в поддержку и завести кастомное правило на аккаунт.
Для домена с систематическими «404 ботам» это стоит сделать — иначе
платишь за каждый.

### Базовая стоимость

| Тип запроса | Кредитов |
|---|---|
| Обычный (датацентровый прокси) | 1 |
| DC + headless (`render=true`) | 5 |
| Residential/mobile (`super=true`) | 10 |
| Residential + headless (`super` + `render`) | 25 |

### Ловушка: серверные per-domain профили

Для ряда доменов scrape.do **включает `super`/`render` сам**, независимо от
твоих параметров, и списывает по тарифу этого профиля. Примеры из таблицы:
`google.*`, `idealista.*`, `capterra.com`, `leboncoin.fr`, `mouser.com`,
`lowes.com` — 10; `g2.com`, `shein.*`, `nordstrom.*`, `realestate.com.au`,
`fastpeoplesearch.com` — 25; `linkedin.com` — 30; `aircanada.com`, `jd.com`
— 75; `shopee.*` — 100; `sainsburys.co.uk` — 200; `carsales.com.au` — 25–200
динамически. `amazon.*` — 1 (маршрутизируется в Amazon Scraper API,
возвращает структурированный JSON).

Практический вывод: **нельзя считать стоимость по своим параметрам**.
Ты можешь отправить «обычный» запрос за 1 кредит и получить счёт на 25.

### Заголовки для учёта — используем вместо оценок

| Заголовок | Что даёт |
|---|---|
| `Scrape.do-Request-Cost` | сколько кредитов списал именно этот запрос |
| `Scrape.do-Remaining-Credits` | остаток кредитов после запроса |

Это закрывает вопрос точности `budget.py`: **не оцениваем стоимость по
таблице, читаем факт из заголовка**. Документация прямо говорит доверять
заголовку, а не таблице. В ClickHouse пишем реальную цифру.

### Внутренние ретраи — источник двойных повторов

scrape.do **сам** повторяет неудачные запросы:

- `retryTimeout` — максимальное ожидание ответа от целевого сайта, после
  которого шлётся новый запрос и цикл повторяется. По умолчанию **15000 мс**,
  допустимо 5000–55000. Документация предупреждает: изменение влияет на
  success rate.
- `disableRetry=true` — отключает их ретраи полностью; вернётся результат
  как есть, успешный или нет.

**Правило для нашей системы:** свою ретрай-логику строим поверх
`disableRetry=true`, либо не ретраим сами вообще. Ретраи с двух сторон —
это латентность в десятки секунд и лишние списания там, где цикл
всё-таки дошёл до тарифицируемого кода.

Дополнительно: при `transparentResponse=true` возвращаются коды целевого
сайта, а проблемы прокси приходят как 502 поверх. Классификатору нужно
различать «502 от scrape.do» и «502 целевого сайта» — это разные вердикты
(`PROVIDER_ERROR` против `ORIGIN_DOWN`), хотя код один.

## Firecrawl

```
last_verified: 2026-08-18
docs: https://docs.firecrawl.dev/ , https://www.firecrawl.dev/pricing
```

- Тарифицируются **только успешные запросы** (официальный FAQ).
- Базовые ставки: Scrape, Crawl, Map, Monitor — 1 кредит за страницу;
  Search — 2 кредита за 10 результатов; Interact — 2 кредита за минуту
  браузера.
- **Множители, которые съедают бюджет:** JSON-формат +4 кредита,
  Enhanced/Stealth Mode для защищённых сайтов — ×5 (5 кредитов/страница).
  Страница с JSON + enhanced доходит до ~9 кредитов. Это главная причина
  «куда делись кредиты».
- **Кредиты не переносятся** на следующий период на self-serve тарифах
  (rollover — только Scale/Enterprise). План берём по средней нагрузке,
  не по пиковой.
- **Исключение по биллингу:** агент FIRE-1 (preview) тарифицируется даже
  при неуспешном прогоне. Нетипично для отрасли, легко пропустить при
  тестировании.
- Конкурентность: параллельные браузеры ограничены планом, лишние задачи
  ждут в очереди, **время ожидания в очереди засчитывается в `timeout`
  запроса**. Практика: ставить меньший timeout, чтобы падать быстро, и
  смотреть Queue Status перед отправкой пачки. Задачи в очереди истекают
  максимум через 48 часов.
- Есть keyless-доступ (лимиты по IP в день) и бесплатный ключ на 1000
  кредитов/мес.
- Отдельно: страницы сверх токенного лимита при extract **молча
  усекаются** — extract отрабатывает и тарифицируется полностью, работая
  с неполными данными. Прямой кандидат в класс «зелёные логи, ноль данных»:
  наш schema-валидатор обязан это ловить.

**Когда берём Firecrawl:** нужен markdown/структурированный выход для
LLM-пайплайна, обход сайта целиком с картой. **Когда не берём:** нужен
просто HTML — дешевле scrape.do; нужен максимальный success rate на
защищённом сайте — дешевле не выйдет из-за ×5.

## Bright Data Web Unlocker

```
last_verified: 2026-08-18
docs: https://docs.brightdata.com/scraping-automation/web-unlocker/
```

- Модель: **оплата только за успешные ответы**, заявленный success rate 98%.
  Ретраи с альтернативными конфигурациями делает сам, до успеха.
- Эндпоинт: `POST https://api.brightdata.com/request`, тело
  `{"zone":"...","url":"...","format":"raw"|"json"}`, авторизация
  `Bearer`. Есть и проксирующий доступ через super proxy —
  результат идентичен, REST рекомендован.

### Ловушка, которая ломает всю экономику

Включение **Custom headers & cookies** переводит биллинг с «только успешные»
на **100% запросов, включая неуспешные**. Причина по документации — Bright
Data теряет полный контроль над запросом. То же и у Browser API.

Это худший из возможных режимов для сайта с высокой долей блоков — ровно
там, где кастомные заголовки и хочется включить. **Запрещаем на уровне
Gateway:** флаг custom headers доступен только с явным апрувом и отдельным,
пониженным дневным лимитом.

Дополнительно: заголовки/куки для логина и аутентификации не разрешены,
кастомные заголовки требуют одобрения комплаенса, и даже после одобрения
падают производительность и success rate.

### Прочее

- **Premium domains** — предопределённый список тяжёлых доменов по
  повышенной ставке; включается явно в настройках зоны и действует только
  на домены из списка, остальной трафик по стандартной ставке.
- `x-unblock-expect` — заголовок, указывающий дождаться конкретного CSS-
  селектора; для пагинации и динамического контента его игнорирование
  приводит к неполным ответам (наш случай «PARSE_FAIL, который на самом
  деле недогруз»).
- Web Unlocker **не** предназначен для Puppeteer/Playwright/Selenium и
  анти-детект браузеров — для этого Browser API. Browser API тарифицируется
  по трафику, включая трафик неудачных попыток.
- Не поддерживает клики, формы, скролл — только выдача контента страницы.
- Для поисковиков — отдельный SERP API (за неуспешные не тарифицирует).
- Есть рекуррентный бесплатный тариф 5000 результатов/мес.
- Мониторинг расхода — колонка Traffic в My Proxies, CPM = стоимость за
  1000 успешных запросов.
- У Bright Data есть **официальный репозиторий скиллов** для агентов:
  `github.com/brightdata/skills` — оттуда стоит взять их best-practices
  как reference, там же продублировано правило про custom headers.

Их же рекомендация, совпадающая с аксиомой №4 нашего скилла: сначала
пробовать прямой API-эндпоинт сайта — часто проходит без доп. настроек
и дешевле.

## Сравнение: что выбирать

| Задача | Провайдер | Почему |
|---|---|---|
| Дёшево HTML, датацентр | scrape.do, 1 кредит | базовая ставка ниже всех |
| HTML + JS-рендер | scrape.do `render=true`, 5 | против Firecrawl ×5 без markdown |
| Markdown/JSON для LLM | Firecrawl | профильный выход, но +4 за JSON |
| Обход сайта целиком с картой | Firecrawl crawl/map | 1 кредит/страница |
| Максимальный success rate | Bright Data Unlocker | 98%, честный pay-for-success |
| Сайт из per-domain списка scrape.do | сравнить с BD | 25–200 кредитов может проиграть |
| Много 404 в очереди | **никакой** | scrape.do тарифицирует 404 |

Общее правило учёта: у scrape.do стоимость читаем из заголовка ответа;
у Firecrawl и Bright Data — считаем по тарифу и сверяем с дашбордом
еженедельно.

## Библиотеки: что изменилось

### Scrapling — пересмотр роли

```
last_verified: 2026-08-18 (v0.4.10, релиз 4 июля 2026)
repo: github.com/D4Vinci/Scrapling
docs: scrapling.readthedocs.io
```

Прошлая оценка «Scrapling для точечных задач, Scrapy для краулинга»
**устарела**. В Scrapling появился полноценный Spider-фреймворк, и он
закрывает почти всё, ради чего брался Scrapy:

- Spider API в стиле Scrapy: `start_urls`, async `parse`, Request/Response.
- Конкурентность с per-domain троттлингом и задержками.
- **Pause & resume через чекпойнты** — Ctrl+C сохраняет прогресс, повторный
  старт с тем же `crawldir` продолжает. Прямо закрывает наше требование
  «прогон переживает падение».
- **Blocked Request Detection** — автоматическое обнаружение и повтор
  заблокированных запросов с настраиваемой логикой. Это точка, куда
  встраивается наш `triage`, вместо написания middleware с нуля.
- Соблюдение robots.txt (`robots_txt_obey`) с `Disallow`, `Crawl-delay`,
  `Request-rate` и кэшем на домен.
- **Development Mode** — кэш ответов на диск при первом прогоне и
  воспроизведение при следующих. Это ровно наш «перепарс без сети» на
  уровне разработки (в проде роль снапшотов остаётся за R2).
- Встроенная ротация прокси (`ProxyRotator`), мульти-сессии в одном
  пауке: часть URL через быстрый HTTP-сеанс, часть — через stealth.
- Adaptive-парсинг: элементы переискиваются после смены вёрстки по
  алгоритмам похожести (`auto_save=True` → позже `adaptive=True`).
  Смягчает `PARSE_FAIL`, но **не отменяет** дрейф-мониторинг.

Фетчеры под наши уровни:

| Уровень | Класс | Замечание |
|---|---|---|
| L1 | `Fetcher` / `FetcherSession(impersonate='chrome')` | браузерный TLS-фингерпринт, HTTP/3 |
| L2 | `StealthyFetcher` / `StealthySession(solve_cloudflare=True)` | Turnstile/Interstitial из коробки |
| L2 (обычный рендер) | `DynamicFetcher` | Playwright Chromium / Chrome |

Дополнительно: блокировка доменов и рекламы в браузерных фетчерах
(экономит CPU и трафик на L2), DNS-over-HTTPS против DNS-утечек при
работе через прокси, Docker-образ со всеми браузерами, MCP-сервер и
**собственный agent-skill в репозитории** (`agent-skill/`) — его стоит
прочитать при написании нашего скилла, чтобы не дублировать.

Установка не тривиальна: `pip install scrapling` ставит **только парсер**;
для фетчеров нужно `pip install "scrapling[fetchers]"` и затем
`scrapling install` (браузеры + зависимости фингерпринта). Питон ≥ 3.10.

**Новая рекомендация:** Scrapling как основной Python-стек и для точечных
задач, и для краулинга. Scrapy оставляем только там, где уже есть готовый
проект на нём или нужны специфические расширения экосистемы.

### Rust: rquest устарел, актуален wreq

```
last_verified: 2026-08-18
```

- `rquest` от 0x676e67 **переименован в `wreq`**; исходный репозиторий
  автора помечен deprecated, `rquest` на crates.io не обновлялся ~5 месяцев,
  тогда как `wreq`/`wreq-util` активны (6.0.0-rc / 3.0.0-rc).
- Актуально: `wreq` + `wreq-util` (100+ профилей эмуляции браузеров,
  `Emulation::Chrome…/Firefox…/Safari26`), плюс `wreq-rt` как рантайм.
- Важная деталь, полезная против WAF: большинство Rust-клиентов через
  `http`-крейт **теряют регистр заголовков**, и часть WAF отклоняет HTTP/1
  с lowercase-заголовками. wreq сохраняет регистр.
- Грабли сборки: конфликт символов `boring-sys` с `openssl-sys` →
  падение линковки или сегфолт в рантайме. Не собирать вместе с крейтами
  на openssl; на Linux/Android помогает фича `prefix-symbols`. Для сборки
  BoringSSL нужны `build-essential cmake perl pkg-config libclang-dev
  musl-tools`.
- Когда нужна **байт-точность** фингерпринта (Akamai, DataDome, Imperva
  сверяют ClientHello и HTTP/2 SETTINGS с User-Agent): in-process клиенты
  вроде wreq дают близкое приближение, но точное совпадение даёт только
  патченный BoringSSL+nghttp2 — обёртка `curl-impersonate-cli` над
  `lexiforest/curl-impersonate` (поддерживаемый форк). Платим
  подпроцессом на каждый запрос. Берём только если wreq не проходит.

Итог для `rust-stack.md`: `wreq` + `wreq-util` + `scraper` + `tokio` —
базовый L1-воркер; `curl-impersonate-cli` — запасной вариант для сайтов,
где нужна байт-точность; `chromiumoxide` — L2, без stealth-преимуществ
перед Python.

### Чёрный список и рабочие инструменты L2

**Не использовать (подтверждено на 2026):**

- `Anorov/cloudflare-scrape`, `cloudscraper` — обходили челлендж CF,
  которого давно нет.
- `puppeteer-extra-plugin-stealth` —深 deprecated с февраля 2025, CF
  детектит патчи на месте.
- FlareSolverr — сопровождение заглохло, тоже флагается.

**Рабочее на L2:**

- **Camoufox** — патчит фингерпринт на уровне C++ Firefox, а не JS.
  Поэтому обходит CF Enterprise там, где JS-патчи Patchright не проходят.
- **Patchright** — Playwright с патчами, дешевле и быстрее Camoufox,
  проходит на средних защитах.
- **Nodriver**, **SeleniumBase UC Mode** — альтернативы под Turnstile.
- **Scrapling StealthyFetcher** с `solve_cloudflare=True` — обёртка над
  этим слоем, не требующая ручной сборки.
- `sarperavci/CloudflareBypassForScraping` — живой, на DrissionPage;
  но учитывать, что README продвигает коммерческий сервис, а не только
  локальное решение. Точечно, не как основа.

Слои защиты CF, к которым это привязано: TLS/HTTP2-фингерпринт (лечится
L1 с curl_cffi/wreq) → репутация IP (прокси) → JS-челлендж и Turnstile
(нужен настоящий браузер, curl_cffi здесь бессилен) → поведенческий
анализ (лечится джиттером 300–2500 мс, а не фиксированным sleep, и
снижением скорости — не сменой IP).

## Что меняется в коде системы

1. `triage.py`: для scrape.do вердикт `DEAD_URL` (404/410) помечается как
   **платный** — счётчик денег обязан его учитывать. Появляется отдельный
   вердикт `PROVIDER_ERROR` только для 502/510/429/401 scrape.do.
2. `budget.py`: стоимость берётся из `Scrape.do-Request-Cost`, а не из
   таблицы. Дневной лимит считается в кредитах и деньгах отдельно по
   провайдерам.
3. Gateway: запрет на Bright Data custom headers/cookies без явного
   апрува; `disableRetry=true` по умолчанию для scrape.do, чтобы не
   ретраить поверх их ретраев.
4. Site Profile: поле `provider_domain_profile` — если домен в
   per-domain списке scrape.do, стартовая стоимость известна заранее и
   L3 может оказаться дороже L4 у другого провайдера. Считать до запуска.
5. Фаза A (HEAD-sweep дешёвым уровнем) повышается из «оптимизации» в
   обязательный этап — из-за тарификации 404.
6. Python-шаблоны переписываются под Scrapling Spiders (чекпойнты,
   blocked detection, robots) вместо Scrapy-проекта.
7. Rust-шаблон: `wreq`/`wreq-util` вместо `rquest`.
