# Killer-фича: Adaptive Cost Router + Freshness Scheduler

Стоимость прогона раскладывается на два множителя:

```
Деньги = (сколько страниц забираем) × (сколько стоит одна страница)
```

Все существующие инструменты работают только со вторым множителем, и то
грубо: ты руками выбираешь уровень и живёшь с ним. Ни один провайдер не
оптимизирует его за тебя — у него противоположный интерес. И никто вообще
не трогает первый множитель.

Фича атакует оба.

- **ACR (Adaptive Cost Router)** — второй множитель: система эмпирически
  находит самый дешёвый уровень, который реально работает на этом домене,
  и держит его актуальным без человека.
- **Freshness Scheduler** — первый множитель: система забирает страницу
  только если есть основания считать, что она изменилась.

Обе живут внутри Fetch Gateway. Парсеры не меняются.

# Часть 1. ACR — самообучающийся роутер по стоимости

## Идея в одном абзаце

Уровень для домена выбирается не человеком и не один раз, а вычисляется
каждый прогон из накопленной статистики: для каждого уровня известны
эмпирическая вероятность успеха и реальная стоимость, и роутер выбирает
стартовый уровень, минимизирующий **математическое ожидание стоимости
одной успешно полученной страницы** при заданной планке полноты. Плюс
непрерывно тратит крошечную долю запросов на проверку, не подешевел ли
сайт.

## Ключевая асимметрия, на которой всё держится

**Разведка вниз бесплатна, эскалация вверх стоит денег.**

Уровни L1 (HTTP с браузерным фингерпринтом) и L2 (локальный stealth-браузер)
не стоят ничего, кроме CPU твоего Ryzen. Значит, проверять гипотезу «а вдруг
сайт уже отдаётся дешевле» можно сколько угодно часто и почти даром — тогда
как проверка «а не пора ли платить больше» стоит реальных кредитов.

Отсюда политика: **вниз пробуем агрессивно и постоянно, вверх поднимаемся
неохотно и только по доказанному вердикту BLOCKED/SOFT_BLOCK.**

Именно это делает фичу невоспроизводимой на стороне провайдера: scrape.do
не знает, что у тебя есть работающий локальный Camoufox, и никогда не
предложит тебе не платить.

## Модель данных

Ключ статистики: `(domain, url_class, level)`, где `url_class` берётся из
Site Profile (например `article`, `listing`, `api`) — на одном домене
карточка товара и страница категории могут иметь разные защиты.

Для каждого ключа хранится в ClickHouse:

```
attempts            — попытки
successes           — вердикт OK ПОСЛЕ валидации контента
p_hat               — EWMA доли успеха (полураспад ~14 дней: сайты меняются)
p_lo                — нижняя граница Уилсона (95%) — рабочая оценка
cost_mean           — средняя фактическая стоимость (из Scrape.do-Request-Cost)
latency_p50, p95    — латентность
last_success_at
last_change_at      — когда детектор дрейфа последний раз сработал
```

### Атрибуция — самое важное правило

Против уровня засчитываются **только** вердикты `BLOCKED` и `SOFT_BLOCK`.

`DEAD_URL`, `ORIGIN_DOWN`, `RATE_LIMITED`, `PROVIDER_ERROR`, `PARSE_FAIL`
— **нейтральны**: они не увеличивают и не уменьшают `successes`, а
исключаются из выборки целиком.

Без этого правила фича превращается во вредителя: сайт полежал ночь с 502,
роутер решил, что L1 «перестал работать», и увёл весь домен на residential.
Это ровно та ошибка, которая сжигала бюджет вручную — автоматизировать её
было бы худшим исходом.

## Формула выбора уровня

Лестница `L1 … Ln` с ценами `c_i` и вероятностями `p_i` (берём `p_lo`).
Ожидаемая стоимость получения одной страницы, если начать с уровня `i`
и каскадировать вниз по лестнице при блоке:

```
E_n = c_n / p_n                      (последний уровень, ретраи сам с собой)
E_i = c_i + (1 - p_i) · E_{i+1}
```

Ожидаемая полнота при старте с `i`:

```
completeness_i = 1 - Π (1 - p_j),  j = i..n
```

Роутер выбирает **минимальный по E_i уровень среди тех, где
`completeness_i ≥ SLO` (0.995) и `latency_p95` укладывается в окно прогона.**

### Пример, почему это не косметика

Домен за Cloudflare. Замеры: L1 p=0.60 (c=0), L2 p=0.90 (c=0),
L3 scrape.do render p=0.97 (c=5), L4 residential p=0.99 (c=25).

```
E4 = 25 / 0.99            = 25.25
E3 = 5 + 0.03 · 25.25     =  5.76
E2 = 0 + 0.10 · 5.76      =  0.58
E1 = 0 + 0.40 · 0.58      =  0.23   ← выбор роутера
```

Полнота при старте с L1: `1 − (0.40·0.10·0.03·0.01) ≈ 99.999%`.

Старт с L3 «чтобы наверняка» стоит **5.76 кредита против 0.23** — в 25 раз
дороже при худшей полноте. Человек, выбирающий уровень на глаз, почти
всегда выбирает слишком высокий: цена ошибки в сторону «дорого» невидима,
а в сторону «блокируют» — заметна сразу. Роутер этой асимметрии не имеет.

Плата за экономию — латентность: 40% страниц потребуют двух попыток.
Поэтому в критерий и входит `latency_p95` против длины окна.

## Shadow-probing: разведка, которая окупается

`ε` от запросов прогона (по умолчанию 3%, отдельный жёсткий cap) идут на
**уровень на ступень ниже текущей политики** — до основного запроса.

Механика важна: если проба успешна и контент прошёл валидацию — **её
результат используется как основной, а платный запрос не делается**.

То есть разведка вниз имеет **отрицательную ожидаемую стоимость**: она либо
подтверждает, что дешевле не выходит (потратив только CPU), либо сразу
экономит цену основного запроса. Это снимает классический конфликт
exploration/exploitation — здесь исследование дешевле эксплуатации.

Отбор проб приоритизируется по «возрасту незнания»: домены, где нижний
уровень не проверялся дольше всего, пробуются первыми.

## Гистерезис и защита от дребезга

- **Понижение уровня** требует `p_lo` (Уилсон) выше порога на выборке
  ≥ 50 проб и в 3 окнах подряд. Две удачные пробы ничего не значат.
- **Повышение уровня** — быстрое: 20 подряд BLOCKED на домене (тот же
  circuit breaker) поднимает уровень немедленно, не дожидаясь статистики.
  Асимметрия сознательная: недобор данных дороже переплаты в моменте.
- Между понижениями одного домена — карантин 72 часа.

## Детектор смены защиты (побочный, но, возможно, главный эффект)

Пробы идут непрерывно, поэтому у системы всегда есть свежая оценка **всех**
уровней, а не только рабочего. CUSUM по `p_hat` нижнего уровня ловит момент,
когда сайт ужесточил защиту, — часто **до того**, как это сломает основной
прогон, потому что деградация видна на пробах раньше, чем доходит до
рабочего уровня.

Срабатывание → `last_change_at`, переразведка всей лестницы (probe.py),
алерт с готовым диагнозом: «example.com: L1 упал 0.94 → 0.31 за 2 дня,
сигнатура CF managed challenge, рекомендованный уровень L2, ожидаемая
стоимость 0».

Это превращает алертинг из «что-то сломалось, иди разбирайся» в
«вот что изменилось и вот что с этим делать».

## Карточка политики домена (артефакт для человека)

```
example.com / article
  политика:      L2 (локальный stealth)      с 2026-08-04
  полнота:       99.7%   (n=4210)
  стоимость:     0.00 кредита/страница       было L3: 5.2
  пробы вниз:    L1 → p_lo 0.44 (n=180)      не проходит
  пробы вверх:   не требуются
  hidden API:    не найден (проверено 2026-07-12)
  смена защиты:  12 дней назад (усиление)
  экономия/мес:  ~21 800 кредитов
```

Это же — ответ на вопрос «почему мы платим за этот сайт»: не «так решили
полгода назад», а измеренный факт с датой.

# Часть 2. Freshness Scheduler — не забирать то, что не менялось

ACR удешевляет запрос. Этот блок убирает сам запрос.

Для регулярного парсинга (твой случай: одни и те же URL по расписанию)
подавляющее большинство страниц между прогонами не меняется. Забирать их
заново — чистая трата.

## Три уровня дешевизны проверки

1. **Условный запрос.** `If-None-Match` / `If-Modified-Since` из сохранённых
   `ETag`/`Last-Modified`. Ответ `304 Not Modified` — тело не передаётся,
   трафика почти нет, у большинства провайдеров такой ответ вне
   тарифицируемых кодов (проверять на конкретном провайдере — у scrape.do
   тарифицируются 2xx/400/404/410, 304 в список не входит).
2. **Хэш контента.** Нормализованный (без таймстемпов, счётчиков,
   рекламных блоков) хэш тела. Совпал — запись не переписывается, вниз по
   пайплайну ничего не идёт, `last_seen` обновляется.
3. **Дешёвый дозор.** Одна страница-индекс (лента, sitemap с `lastmod`,
   listing с датами) сообщает о десятках изменившихся URL за один запрос.
   Забираем только их.

## Адаптивный интервал перепроверки

На каждый URL копится частота изменений. Интервал перепроверки
подстраивается: страница, не менявшаяся 90 дней, проверяется раз в неделю;
менявшаяся вчера — каждый прогон. Классический экспоненциальный backoff, но
по признаку изменчивости, а не ошибки.

Аварийный клапан: **полная ревизия** (все URL, игнорируя интервалы) раз в
N дней — чтобы «уснувшие» страницы не выпали из поля зрения навсегда.

## Переопределение метрики полноты

Это меняет смысл SLO — и в лучшую сторону:

> **Полнота = доля записей, актуальных в пределах своего окна свежести.**
> Не «сколько URL мы скачали за ночь».

При такой формулировке 100% достижимы честно и дёшево: не нужно каждую
ночь тащить 20 000 статей, нужно доказать, что все 20 000 записей свежие.
Прогон, скачавший 300 изменившихся страниц и подтвердивший 19 700
неизменившихся, — это 100% полноты, а не 1.5%.

# Как это ложится в архитектуру

Обе фичи живут в Fetch Gateway и меняют только шаги 1 и 3 его конвейера:

```
1. Дедуп/идемпотентность
1b. ← Freshness Scheduler: нужен ли вообще запрос?
        нет → отдать сохранённое, стоимость 0
        да  → условный запрос (ETag) → 304? → тоже стоимость 0
2. Бюджет-гейт
3. ← ACR: выбор стартового уровня + решение о shadow-probe
4–9. Исполнение, triage, валидация, учёт, каскад, снапшот
        ↓
   статистика (domain, url_class, level) → ClickHouse → обратно в ACR
```

Парсеры, Site Profile и шаблоны не трогаются. ACR читает те же метрики,
которые система и так пишет, — фича почти целиком строится на уже
спроектированном фундаменте, новый только слой принятия решения.

## Требования-предпосылки (без них фича вредна)

1. **Валидация контента работает.** Если капча-страница считается успехом,
   роутер выучит, что L1 отлично работает, и уведёт домен туда навсегда.
   Обучение поверх сломанной валидации хуже, чем отсутствие обучения.
2. **Атрибуция вердиктов корректна** (правило выше).
3. **Учёт стоимости фактический** (`Scrape.do-Request-Cost`), не оценочный.
4. **Сырьё в R2** — иначе решения роутера нечем аудировать постфактум.

## Гарантии и предохранители

| Риск | Предохранитель |
|---|---|
| Роутер учится на мусоре | канареечный селектор + схема; ручной аудит 20 случайных страниц/нед |
| Пробы съедают бюджет | пробы только вниз (бесплатные уровни), жёсткий cap ε |
| Дребезг уровней | Уилсон + 3 окна + карантин 72ч |
| Downgrade ломает прогон | понижение действует со следующего прогона, не в середине |
| Сайт лежит → ложная эскалация | ORIGIN_DOWN нейтрален для статистики |
| Freshness пропустил изменение | полная ревизия раз в N дней + канареечная выборка |
| Роутер «застрял» на дорогом уровне | пробы вниз идут всегда, даже при 100% успехе наверху |

## Метрики самой фичи

- `saved_credits` — разница между фактической стоимостью и стоимостью
  «наивной политики» (человек выбрал уровень и не менял). Главное число
  для дашборда: сколько фича заработала.
- доля прогона, обслуженная бесплатными уровнями
- доля запросов, снятых Freshness Scheduler (не сделанных вообще)
- среднее время от смены защиты сайта до срабатывания детектора
- число ложных понижений (понижение → откат внутри недели)

## Definition of Done

1. На эталонном наборе ACR за 7 прогонов сходится к тому же уровню, что
   выбрал бы эксперт вручную, минимум на 2 из 3 сайтов, и **дешевле** на
   третьем.
2. Искусственное ужесточение защиты (включение CF challenge) детектируется
   пробами не позже, чем через 1 прогон, до падения completeness.
3. Искусственное ослабление защиты приводит к автоматическому понижению
   уровня в пределах 3 прогонов без ручного вмешательства.
4. Сутки с лежащим origin не вызывают ни одной эскалации уровня.
5. Freshness Scheduler на неизменившемся корпусе даёт ≥ 90% снятых
   запросов при 100% полноты по определению «актуальность в окне».
6. Дашборд показывает `saved_credits` за месяц с разбивкой по доменам.

## Место в roadmap

ACR встаёт **этапом 7.5** — после наблюдаемости (нужны метрики) и Data
Quality (нужна валидация), до Rust-порта. Freshness Scheduler можно ставить
раньше, этапом 5.5: он не требует обучения и даёт экономию сразу.

Порядок внедрения по возрастанию отдачи на единицу труда:
`ETag/304` → `хэш контента` → `адаптивный интервал` → `ACR shadow-probes`
→ `ACR полная политика` → `детектор смены защиты`.
