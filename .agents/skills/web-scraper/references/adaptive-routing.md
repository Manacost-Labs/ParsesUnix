# Adaptive Cost Router и Freshness Scheduler

Внедрять только после стабильной валидации контента, правильной атрибуции вердиктов, фактического учёта стоимости, снапшотов и наблюдаемости. Иначе автоматизация усиливает ошибочные решения.

## Freshness Scheduler — раньше

Порядок реализации:

1. `ETag`/`If-None-Match` и `Last-Modified`/`If-Modified-Since`.
2. Нормализованный content hash.
3. Sitemap/listing как дешёвый дозор изменений.
4. Адаптивный интервал по истории изменения URL.
5. Периодическая полная ревизия и канареечная выборка.

Полнота означает долю записей, свежесть которых доказана в пределах их окна, а не долю повторно скачанных URL.

## Adaptive Cost Router — позже

Ключ статистики: `(domain, url_class, route, level)`. В рабочую выборку успеха включать только `OK`, `BLOCKED`, `SOFT_BLOCK`. `DEAD_URL`, `ORIGIN_DOWN`, `RATE_LIMITED`, `PROVIDER_ERROR`, `AUTH_REQUIRED`, `ACCESS_DENIED`, `THIN_CONTENT` и `PARSE_FAIL` нейтральны для оценки способности уровня пройти защиту.

Хранить attempts, validated successes, EWMA, нижнюю границу Уилсона, фактическую стоимость, p50/p95 и даты изменений.

Для лестницы уровней с ценой `c_i` и консервативной вероятностью успеха `p_i`:

```text
E_n = c_n / p_n
E_i = c_i + (1 - p_i) * E_(i+1)
completeness_i = 1 - product(1 - p_j), j=i..n
```

Выбирать минимальное `E_i`, которое выполняет SLO полноты и ограничение окна по p95.

Shadow probe делать только на более дешёвый уровень, с малым cap. Успешный результат использовать как основной. Понижение требовать по консервативной статистике в нескольких окнах; повышение разрешать быстро при устойчивом `BLOCKED`. Между понижениями держать гистерезис.

Ключевые метрики: saved credits, доля бесплатных запросов, снятые freshness-запросы, время обнаружения смены защиты и ложные понижения.
