# Контроль стоимости

## Кто решает платить

Не роутер. Решение о платном уровне принимает **triage** — только по вердиктам
`BLOCKED`/`SOFT_BLOCK` — и оно проходит через бюджет. Провайдерский роутер
отвечает на другой вопрос: *«раз платить разрешено, какой стратегией?»*

До triage действует ещё один независимый барьер: ordered allowlist
`allowed_providers` из run config. Ключ в окружении только делает адаптер
доступным, но не разрешает вызов. Пустой allowlist означает ноль платных
провайдеров; это безопасное значение по умолчанию.

## Задача роутера

```
минимизировать ожидаемую стоимость
при условии  надёжность >= целевой
```

Надёжность — нижняя граница Уилсона по **валидированным** успехам конкретной
стратегии. Не по провайдеру целиком: провал `normal` на домене ничего не говорит
о том, сработает ли там `super`.

## Порог надёжности — это НЕ доля успехов

Сравнение идёт с *пессимистичной* нижней границей. При идеальной истории:

| Наблюдений | Нижняя граница |
|---:|---:|
| 10/10 | 0.722 |
| 20/20 | 0.839 |
| 40/40 | 0.912 |
| 70/70 | 0.948 |
| 200/200 | 0.981 |

Отсюда практический вывод: **порог 0.95 требует около семидесяти подряд
валидированных успехов**. Поставив его «для надёжности», вы получите роутер,
который отказывает всем стратегиям. По умолчанию — `0.80`, достижимо примерно с
15 чистых наблюдений; поднимать точечно для тех классов URL, которые этого
действительно заслуживают.

## Стратегия должна отвечать на проблему

Платить за возможность, которая не лечит наблюдаемый отказ, — самый быстрый
способ потратить бюджет впустую.

| Возможность | Отвечает на | Не отвечает на |
|---|---|---|
| премиальная сеть (`super`) | `BLOCKED`, `SOFT_BLOCK` | `CSR_REQUIRED`, `PARSE_FAIL`, `ORIGIN_DOWN` |
| рендеринг (`render`) | `CSR_REQUIRED`, `SOFT_BLOCK` | `BLOCKED`, `DEAD_URL`, `ORIGIN_DOWN`, `PARSE_FAIL` |

Жёсткий `403` рендерингом не пробивается: WAF откажет и отрендеренному запросу, а
стоить это будет впятеро дороже.

## Резервация бюджета

Гонка не внутри записи расхода, а между проверкой и самим вызовом: N воркеров
проходят проверку и все тратят. Поэтому кредиты **резервируются до вызова**:

```
reserve(estimate)   ->  держим кредиты, лимит проверяется здесь
   вызов провайдера
settle(actual)      ->  запись фактической стоимости из заголовка
release()           ->  вызова не было, ничего не списано
```

Проверено: 20 потоков при лимите 10 кредитов дают ровно 10 разрешённых, 10
отказов и ноль зависших резерваций.

## Стоимость, которую не удалось определить

Если провайдер не сообщил стоимость, вызов помечается `unattributed` и считается
**не бесплатным**. Молча обнулённый расход — это как превышают бюджет.

## Объяснимость

Любое платное решение печатается:

```
provider: scrape.do
escalation verdict: BLOCKED
reliability target: 0.800
   normal        cost   1  reliability 0.000  0/20 validated, below target 0.800
   render        cost   5  reliability 0.000  rendering does not address BLOCKED
-> super         cost  10  reliability 0.839  20/20 validated
```

# Денежная безопасность: что именно гарантируется

Честная формулировка гарантии важна, потому что широкая была бы ложью. Внешний
провайдер может списать больше, чем мы оценили, **после** того как запрос ушёл —
этому нельзя помешать из нашего процесса.

Гарантируется следующее:

1. ни один платный вызов не начинается **сознательно** без достаточного резерва;
2. фактический расход записывается честно, даже если он превысил резерв;
3. расход, который не удалось подтвердить, **останавливает** дальнейшие траты, а
   не списывается в ноль;
4. сбой процесса не приводит к слепой повторной оплате.

## Почему резерв делается ДО вызова

Гонка не внутри записи расхода, а между проверкой и вызовом:

```
проверил лимит   ->   вызвал провайдера   ->   записал расход
                 ^^^^^^^^^^^^^^^^^^^^^^^^
                 здесь N воркеров уже потратили
```

Поэтому кредиты держатся с момента резервации, и лимит проверяется против них.

## Почему резервируется worst-case, а не типовая цена

У стратегии две цены: `nominal_cost` (типовая) и `reservation_cost`
(консервативная). Резерв в 1 кредит против фактического списания в 10 — это
пробитый лимит, при котором каждая отдельная проверка прошла успешно.

| Стратегия | Типовая | Резерв |
|---|---:|---:|
| normal | 1 | 3 |
| render | 5 | 10 |
| super | 10 | 25 |
| super_render | 15 | 30 |

## Состояния бюджета

| Состояние | Платные вызовы | Смысл |
|---|---|---|
| `OK` | да | норма |
| `WARNING` | да | использовано ≥80% лимита |
| `EXHAUSTED` | нет | лимит исчерпан; бесплатный сбор продолжается |
| `OVERSPENT` | **нет** | провайдер списал больше резерва — инцидент |
| `UNKNOWN_SPEND` | **нет** | расход не подтверждён — инцидент |

`OVERSPENT` и `UNKNOWN_SPEND` требуют человека. Прогон не снимает их сам.

## Жизненный цикл резервации

```
RESERVED    деньги удержаны, запрос НЕ отправлен
SUBMITTED   запрос ушёл; провайдер мог списать
SETTLED     фактическая стоимость записана
RELEASED    вызова не было, ничего не списано
UNKNOWN     ушёл, но результат неизвестен — деньги остаются удержаны
```

Разница между `RESERVED` и `SUBMITTED` — это и есть то, что делает возможным
восстановление после сбоя.

## Восстановление после сбоя процесса

Раннер выполняет его **до** любых новых трат:

| Найдено | Действие | Почему |
|---|---|---|
| `RESERVED` | отпустить | запрос не уходил, списания не было |
| `SUBMITTED` | → `UNKNOWN` | мог быть оплачен; угадывать нельзя |

`UNKNOWN` продолжает удерживать сумму и блокирует платную работу до разбора.

### Сценарии

**Сбой после отправки, стоимость неизвестна**

```bash
ws-budget --db state/budget.sqlite3 pending          # что зависло
ws-budget --db state/budget.sqlite3 recover --dry-run
ws-budget --db state/budget.sqlite3 recover          # exit 1, если есть unknown
# найти запрос по provider_request_id в панели провайдера, затем:
ws-budget --db state/budget.sqlite3 reconcile \
    --reservation-id <id> --actual-credits 12 --detail "провайдерская панель"
```

**Провайдер не вернул стоимость.** `settle(actual=None)` не записывает ноль: это
`UNKNOWN_SPEND`, деньги остаются удержаны, платная работа останавливается.

**Перерасход.** Факт записывается как есть, в аудит попадает событие `overspend`
с обеими суммами, состояние становится `OVERSPENT`, дальнейшие резервации
отклоняются.

## Аудит

Каждый переход оставляет след: `created → submitted → settled → overspend` и т.д.
Токены и сырые URL не сохраняются — только хеш цели.

## Платный уровень в шлюзе

`FetchGateway` принимает необязательный `paid_escalator`. **Без него шлюз
бесплатен по построению** — в коде нет ветки, которая тратит деньги, когда
аргумент не передан. Это проверяется тестом, а не обещанием в документации.

Когда эскалатор передан, он запускается **после** исчерпания всех бесплатных
маршрутов и только для `BLOCKED`/`SOFT_BLOCK`. Ровно одна платная попытка на URL.

```python
gateway = FetchGateway(
    profile,
    paid_escalator=PaidEscalator(
        ScrapeDoProvider(),          # токен только из SCRAPE_DO_TOKEN
        budget=BudgetLedger(path, daily_credit_limit="500"),
        router=PaidProviderRouter(stats=route_stats),
    ),
)
```

Отказ платить — тоже запись в отчёте: `Attempt` уровня L3 с причиной и вердиктом,
который установили бесплатные маршруты. Прогон, показывающий только состоявшиеся
вызовы, не может ответить на вопрос «почему этот URL остался заблокирован».

### Живое измерение сквозного пути

Бесплатный маршрут подменён на всегда-`BLOCKED`, провайдер настоящий, цель —
песочница `books.toscrape.com`:

| Что | Значение |
|---|---|
| Маршруты | `L1 BLOCKED` → `L3 OK` |
| Стратегия | `normal` (дешёвая, порог уверенности пройден) |
| Удержано | 3 кредита (worst case) |
| Списано | 1 кредит (`Scrape.do-Request-Cost`) |
| Удержание после прогона | 0 |
| Состояние бюджета | `OK` |

Резерв worst-case строго больше факта — и полностью снят. Именно этот зазор не
даёт параллельным воркерам совместно уйти за дневной лимит.
